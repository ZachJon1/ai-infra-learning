# Day 43 — Model Warmup and Cold Starts

**AI Infrastructure & ML Systems — 220-Day Roadmap**  
**Phase 3: Model Serving / Inference Infrastructure**  
**Topic:** Cold-start latency, PyTorch model warmup, FastAPI readiness, and Kubernetes startup probes

## Overview

An inference service may respond slowly when it first starts because it needs to initialize its runtime, prepare the model, and execute its first operations. This lab measures the difference between a model's **first forward pass** and **steady-state inference**, then uses FastAPI's application lifespan to warm up a GPU-backed model before making it available for HTTP requests.

The lab was executed locally on a **CUDA-enabled system**. The PyTorch model is intentionally small and synthetic to isolate first-use overhead; it is not a benchmark of a real pretrained model or a production GPU serving stack.

### Learning objectives

- Distinguish container startup, model loading, first-inference overhead, and steady-state inference.
- Measure CUDA execution time correctly using synchronization.
- Compare first-inference latency with warm p50, p95, and p99 latencies.
- Warm up a model during FastAPI application startup.
- Understand how Kubernetes startup, readiness, and liveness probes relate to model availability.
- Explain why warmup and readiness delays can affect autoscaled inference services.

## Part 1 — Benchmark cold vs. warm inference

Run:

```bash
python3 benchmark.py
```

### Benchmark methodology

The benchmark constructs this network:

```text
Input: [32, 1024]
   ↓
Linear(1024, 2048)
   ↓
ReLU
   ↓
Linear(2048, 1024)
   ↓
Output: [32, 1024]
```

It selects CUDA if available and then:

1. Creates the model and input on the selected device and records their **setup time**.
2. Synchronizes CUDA before and after each timed forward pass to capture completed GPU execution.
3. Records the **first forward pass** separately.
4. Runs **five warmup passes**.
5. Records **100 steady-state passes** and reports median (p50), p95, and p99 latency.
6. Writes per-pass timing data to `latencies.csv`.

The code uses `torch.inference_mode()` for inference and `time.perf_counter()` for wall-clock timing. Synchronization matters because CUDA kernel launches are normally asynchronous relative to the host CPU.

### Actual results — October 27, 2026

Two separate local Python process runs produced:

| Metric | Run 1 | Run 2 |
|---|---:|---:|
| Device | CUDA | CUDA |
| Model/input setup | 146.290 ms | 124.476 ms |
| First inference | 79.383 ms | 53.176 ms |
| Warm p50 | 0.116 ms | 0.111 ms |
| Warm p95 | 0.144 ms | 0.118 ms |
| Warm p99 | 0.314 ms | 0.320 ms |
| First inference / warm p50 | ~684× | ~479× |

**Interpretation:** In these two runs, the first forward pass took hundreds of times longer than the median warmed-up pass. Potential explanations include first-use GPU runtime and library setup, kernel loading, or other lazy initialization. These measurements alone do **not** identify the precise source of overhead. They also show some variability between fresh processes.

**Measurement boundary:** The model/input setup measurement covers creation, device placement, and input allocation, **not** loading model weights from disk. The first-forward measurement is **not** a full container or Kubernetes cold-start measurement. Results may vary with GPU model, driver/software versions, GPU utilization, input shapes, and concurrent work.

## Part 2 — Warmup in FastAPI

Run the application locally:

```bash
python3 -m uvicorn app:app --host 127.0.0.1 --port 8000
```

At startup, the FastAPI lifespan function:

1. Marks the application as not ready.
2. Creates the PyTorch model on the selected device.
3. Prepares a fixed synthetic input tensor.
4. Executes **five warmup passes** under `torch.inference_mode()`.
5. Synchronizes CUDA so warmup finishes before readiness is reported.
6. Sets `app.state.ready = True` and starts serving requests.

The example app exposes:

| Endpoint | Purpose | Verified result |
|---|---|---|
| `GET /live` | Basic process liveness | `{"status":"alive"}` |
| `GET /ready` | Report successful startup warmup | `{"status":"ready"}` |
| `GET /predict` | Run inference on a **fixed synthetic input** and return the output mean | HTTP 200 with JSON prediction |

Check each endpoint:

```bash
curl -sS -i http://127.0.0.1:8000/live
curl -sS -i http://127.0.0.1:8000/ready
curl -sS -i http://127.0.0.1:8000/predict
```

Measure one end-to-end HTTP request:

```bash
curl -s -o /dev/null \
  -w 'HTTP latency: %{time_total}s\n' \
  http://127.0.0.1:8000/predict
```

### Actual FastAPI results

```text
Device: cuda
Model ready after 0.223s
```

Successful prediction response (actual observed value):

```json
{"prediction":-0.0010513275628909469}
```

The user verified `HTTP/1.1 200 OK` for `/predict`. One measured request took:

```text
HTTP latency: 0.003893s
```

That is **3.893 ms** of local end-to-end HTTP request time, compared with a warm GPU-forward median of approximately **0.11 ms** in the separate benchmark. These are **different measurements**: the HTTP request includes application handling, serialization, and returning a scalar value (which synchronizes the GPU), while the forward-pass benchmark isolates a synchronized model call. A single HTTP timing sample is not a robust latency percentile.

### Request path

```text
Start FastAPI process
        ↓
Create model + input on GPU
        ↓
Run 5 warmup passes
        ↓
Synchronize CUDA
        ↓
Mark app ready
        ↓
HTTP /predict → forward pass → JSON response
```

## Part 3 — Kubernetes probe design (proposed, not deployed)

The following is an **example container-spec fragment** for a Deployment. It was discussed in the lab but **not validated by deploying it to Kubernetes**.

```yaml
ports:
  - containerPort: 8000

startupProbe:
  httpGet:
    path: /ready
    port: 8000
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 24

readinessProbe:
  httpGet:
    path: /ready
    port: 8000
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2

livenessProbe:
  httpGet:
    path: /live
    port: 8000
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3
```

For a containerized deployment, bind Uvicorn to `0.0.0.0` rather than the local-only `127.0.0.1` address:

```bash
python3 -m uvicorn app:app --host 0.0.0.0 --port 8000
```

**Probe responsibilities**

- **Startup:** Allows the application enough time to initialize. With `periodSeconds: 5` and `failureThreshold: 24`, the configured allowance is approximately 120 seconds (actual probe timing can differ).
- **Readiness:** Controls whether the Pod is eligible for normal Kubernetes Service traffic.
- **Liveness:** Triggers a restart after repeated failures indicating that the process is unhealthy.

In this application, the lifespan function blocks server availability until the warmup finishes. Therefore, during startup, `/ready` may simply be unreachable; this is expected and the startup probe must tolerate it. A startup probe is not responsible for downloading images or performing model initialization—it only checks progress after the container starts.

### Troubleshooting scenario studied

An HPA increases desired replicas from **2 to 5**, but three new replicas each need approximately:

| Initialization step | Time |
|---|---:|
| Load model weights | 40 s |
| CUDA initialization | 15 s |
| Model warmup | 10 s |
| **Total** | **65 s** |

With a startup probe configured as `periodSeconds: 5` and `failureThreshold: 6` (roughly 30 seconds), the containers may restart before finishing initialization. Increasing the failure threshold to **24** preserves frequent checks and provides a larger initialization window. Restart backoff delays retries; it does **not** grant an individual startup attempt extra initialization time.

While new replicas are not ready, existing replicas carry the traffic. Queueing and latency can increase; throughput may plateau at existing capacity rather than necessarily decrease. To verify recovery on a real cluster:

```bash
kubectl get pods -w
kubectl get deployment
kubectl describe pod <pod-name>
kubectl logs <pod-name>
kubectl rollout status deployment/<deployment-name>
```

Also verify replica readiness (target: **5/5** in this scenario), restart counts, Service endpoint eligibility, request latency percentiles, throughput, and GPU utilization.

## Limitations and next improvements

- **Synthetic model only:** This lab does not yet load pretrained weights from a checkpoint, remote artifact store, or cache.
- **Fixed inference input:** `/predict` demonstrates execution but is not a real request-driven inference API.
- **Readiness is currently static after warmup:** The boolean does not automatically change if the GPU or model fails later; dynamic model-health reporting remains to be implemented.
- **No Kubernetes rollout yet:** The probe manifest is proposed, not proven through a running Kubernetes Deployment.
- **Limited performance sampling:** Two separate forward-pass benchmark runs and one HTTP request time are recorded; they are not comprehensive workload or concurrency tests.
- **No full cold-start time measurement:** Container creation, image pulling, model downloads, and readiness latency have not been measured as a complete sequence.

Suggested follow-up work: persist the GPU/software environment in benchmark metadata; repeat process starts and HTTP tests under controlled load; implement a real model loader and cache (Day 44); integrate warmup into the existing containerized inference service; deploy and verify Kubernetes probes; document startup and serving metrics before and after optimization.

## Key takeaways

A **cold start** includes initialization work that happens before an inference service is ready, whereas **first-inference latency** measures the first forward pass and **steady-state latency** measures the warmed execution path. Warmup can remove substantial first-use overhead, but cannot guarantee constant latency under varied workloads. Accurate CUDA timings require synchronization or appropriate CUDA Events. In Kubernetes, configure startup probes to tolerate model initialization, readiness probes to gate serving availability, and liveness probes to detect sustained process failures. For autoscaling, the delay before additional replicas become ready matters alongside their steady-state inference speed.
