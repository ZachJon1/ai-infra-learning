Kubernetes, unboxed Day 9: Kubernetes fundamentals for AI infrastructure

Why Kubernetes

Kubernetes, unboxed

On Day 7, Pid learned to live in a container.

Now there are many Pids, spread across many machines.

Kubernetes keeps them running the way you asked, even when things break.

Too many moving parts

Picture an AI service: dozens of inference replicas, workers, databases, metrics agents.

Without an orchestrator, someone has to answer these questions, all day, every day.

Kubernetes answers them continuously, for you.

From starting things to keeping things

Docker runs containers. Compose coordinates them on one host.

Kubernetes orchestrates workloads across a whole cluster.

The real shift: from “start this” to “keep it like this.”

Desired state, actual state

You declare the desired state: replicas: 3. Like setting a thermostat.

A Pod disappears. The actual state drops to 2.

A controller spots the gap and creates one new Pod.

Compare, correct, repeat. That loop is called reconciliation.

Meet the crew

A cluster has a control plane (the brains) and worker nodes (the muscle).

Control plane: API server, scheduler, controller manager, and etcd.

Each worker node runs a kubelet, a container runtime, and your Pods.

In Minikube, one machine plays both roles.

Everything goes through the front door

kubectl get pods talks to the API server over HTTPS, not straight to the scheduler or a kubelet.

The API server is the hub. The scheduler, controllers, and kubelets all talk to it.

etcd is its durable memory: the store where cluster state lives.

Where vs. make it run

A new Pod waits, Pending, with no node assigned.

The scheduler checks free resources and constraints, then picks a node.

The kubelet on that node works with the runtime to start the containers.

Scheduler = where. kubelet = make it run there.

See it in the events

kubectl describe pod lists what happened, in order.

The first event comes from the scheduler. The rest come from the kubelet.

The architecture diagram becomes evidence you can check.

Pods: the smallest thing Kubernetes schedules

Kubernetes schedules Pods, not bare containers. Usually one container per Pod.

Sometimes a sidecar joins. Containers in a Pod share its network identity and can share volumes.

Pods get IPs from the Pod network, separate from the node’s own IP.

Deleted Pods: gone or replaced?

A bare Pod has no controller watching over it.

Delete it, and it’s simply gone.

Delete a Deployment’s Pod, and the ReplicaSet sees 2 of 3 and creates a new one.

Not restarted: replaced, with a new name and often a new IP.

Deployment, ReplicaSet, Pods

A Deployment manages a ReplicaSet. The ReplicaSet keeps the Pod count right.

Names nest like a family tree. Never treat the random suffixes as permanent.

DESIRED: should exist. CURRENT: do exist. READY: are reporting Ready.

You work with Deployments. ReplicaSets come along automatically.

Scale out: more copies, same recipe

kubectl scale --replicas=3 turns 1 Pod into 3, all from the same template.

Horizontal scaling = how many copies. Vertical scaling = how big each one is.

Inference replicas often scale out. Heavy jobs may need bigger Pods.

Requests and limits

A request is what the scheduler sets aside when it places the Pod.

A limit is the most the container may use.

CPU comes in millicores: 1000m = 1 CPU.

No requests or limits at all? The Pod can land in the BestEffort QoS class.

Pod IPs don’t stay put

Three Pods, three IPs. A client hard-codes one of them.

That Pod is replaced. The new one gets a new IP, and the client’s calls fail.

A Service gives the group one stable name and ClusterIP.

Clients call the Service. Pods behind it can come and go.

Labels and selectors

A Service doesn’t track Pod names. Its selector matches Pod labels.

app=day9-web attracts two Pods. The database Pod isn’t selected.

Typo trap: selector app=inference, but Pods labeled app=model-server.

The Service exists, yet it has zero backends.

Names in, endpoints out

An EndpointSlice lists the ready Pod IPs behind a Service, and updates as Pods change.

Inside the cluster, clients just use the name: http://day9-web-service.

CoreDNS turns the name into the Service’s address. The Service forwards to a ready Pod.

Reading Kubernetes YAML

Read top-down. Each field answers a question: which API, what kind, what name?

spec holds the state you want: how many replicas, which Pods to match, what new Pods look like.

The selector and the template labels must match.

A Service finds these Pods with the same label.

Change the file, not the cluster

Edit the YAML: replicas: 2 becomes replicas: 4.

kubectl diff previews the change. kubectl apply makes it so.

The template didn’t change, so no new ReplicaSet: the existing one adds 2 Pods.

Treat the file as the source of truth. Live edits make file and cluster drift apart.

Rolling update

Change the image: nginx:alpine becomes nginx:1.29-alpine.

The Pod template changed, so the Deployment creates a new ReplicaSet.

New Pods scale up, old ones scale down, and traffic follows the Ready Pods.

The old ReplicaSet stays at 0, keeping rollout history.

Rollback adds history

kubectl rollout undo brings back the previous Pod template.

It doesn’t erase history: the rollback is recorded as a new revision.

With YAML in Git, prefer reverting the file and re-applying, so file and cluster stay in sync.

The whole chain

You declare objects. The API server accepts the desired state.

Controllers create ReplicaSets and Pods. The scheduler picks a node; the kubelet starts the containers.

A Service and DNS give clients stable access to whichever Pods match.

Unreachable? Follow the chain

Don’t guess. Walk the relationships in order.

Classic case: Deployment 3/3, Pods Running, Service exists… but no endpoints.

Next check: compare the Service selector with the Pod labels.

Ask which relationship connects two objects, then check that link.

The whole picture

Kubernetes is a desired-state control system: declare it, and controllers keep it true.

Deployments roll out, ReplicaSets keep count, the scheduler places, kubelets run.

Pods are disposable. Services give stable access through labels.
