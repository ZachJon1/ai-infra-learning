Teach mounts to survive a reboot

/etc/fstab is the building’s door list. Linux reads it at boot to decide what to mount where. One line, six fields:

Device names can change order between boots. A UUID is the filesystem’s fingerprint, so it stays with the right data.

Look, don’t touch.Inspect with cat /etc/fstab lsblk -f findmnt sudo blkid. Never format a real partition to practice. In a throwaway lab: back up fstab, check the UUID, test with sudo mount -a and findmnt before rebooting.

Waiting in line counts as time

A request’s latency is the time it spends queued plus the time the device spends serving it.

r_await / w_await: the whole trip, in ms

Conceptual, not to scale

%iowait

CPU side. Share of time the CPU sat idle while I/O was pending. A percentage, not a delay.

≠
r_await

Device side. Average milliseconds per read request, queue time included.

A queue alone isn’t trouble: NVMe drives work on many requests in parallel. Trouble looks like queue rising, latency rising, and throughput going flat.

Who’s raiding the pantry?

iostat says the disk is busy. iotop says who’s keeping it busy.

  1. iostat -xz 1Is the disk busy?
  2. sudo iotop -oPWhich process is reading?
  3. Look inside the appWhy is it asking for so much?

Suspect found: the training job

The tools count over different time windows, so “close” is enough. A 2-second job can slip between iotop refreshes, so loop it while you watch.

Try it on your own machine, safely

Any Linux box with sysstat (and optionally iotop), plus about 3 GiB free. No partitioning, no formatting.

Write down what backs /home and how full it is.

B

Find heavy folders

Note the biggest folder. Look, don’t delete.

C

Watch a direct write

Does IOPS × request size match wkB/s?

D

Cold read, warm read

dd … iflag=directddfree -h

Which read hit the disk, and which hit RAM?

E

Catch the culprit

sudo iotop -oPfor i in {1..10}; do dd …; done

Spot dd and its DISK READ rate.

Lab safety rulesThe only file you delete is your own io-test.bin. Never write to /dev/nvme…, format a partition, run rm -rf on caches, or test with a real model checkpoint.

Your seven-question checklist

Work top to bottom. Each answer tells you which tool to reach for next.

  1. What backs this path?lsblk -ffindmntFind the device, filesystem and mount
  2. Out of bytes?df -hIf yes, find the hog safely with du
  3. Out of inodes?df -iLook for floods of tiny files, or quotas
  4. Is the storage path slow?iostat -xz 1Read latency, rate, size and queue together
  5. Who is doing the I/O?sudo iotop -oPName the process and its access pattern
  6. Is the cache fooling me?free -hiflag=directCompare warm-cache and direct reads
  7. Is the GPU waiting for data?batch timingsGPU metricsMeasure samples/sec and batch wait time
