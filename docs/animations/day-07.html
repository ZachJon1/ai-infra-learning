Docker, unboxed Day 7: Docker fundamentals for AI infrastructure

Why containers

Docker, unboxed

Meet Pid, an ordinary Linux process.

Today Pid moves into a container.

Spoiler: a container isn’t a tiny computer. It’s a process with boundaries.

“It works on my machine”

Pid runs perfectly on your laptop…

…then breaks on the server: different Python, a missing library, another CUDA.

A container ships the app together with its userspace.

The host still lends the kernel and the hardware.

Houses vs. apartments

A virtual machine is a house: it brings its own foundation, a guest kernel.

Containers are apartments sharing one foundation: the host kernel.

Sharing the kernel means fast starts and smaller images.

It also means security and compatibility depend on that host kernel.

Namespaces: what Pid can see

Each namespace gives a process its own private view of one system resource.

Same process, two views: PID 152474 on the host, PID 1 inside the container.

Different hostname? That’s the UTS namespace, not PID.

cgroups: how much Pid can use

The host has plenty: 16 logical CPUs and 31 GiB of RAM.

A cgroup sets Pid’s budget: 2 CPUs’ worth of time and 2 GiB of memory.

Namespaces limit what Pid sees. cgroups limit how much Pid uses.

Recipe, cutter, cookies

Dockerfile: the recipe, plain-text build instructions.

Image: the cookie cutter, a frozen, reusable template.

Container: one cookie stamped from it, running or stopped.

Registry: the shelf where images are shared, like Docker Hub.

A container lives as long as PID 1

A container moves through four states.

It stays running while its main process, PID 1, is alive.

PID 1 exits, the container stops. Remove it when you’re done.

That’s why hello-world exits at once: it prints, finishes, and stops with code 0.

-p 8080:80, traced

You start Nginx and publish a port:

docker run -d --name day7-nginx \
  -p 8080:80 nginx:alpine

curl knocks on host port 8080. Docker forwards it to port 80 inside.

Nginx never moved. It still listens on 80 in its own network namespace.

The bridge: a shared hallway

By default, containers plug into Docker’s bridge network.

docker0 is the hallway. Each container gets its own door: an IP address.

Something unreachable? Ask the same three questions every time.

Four lines, one image

FROM picks a starting image: Linux userspace plus Python 3.11.

WORKDIR sets /app. COPY brings in app.py.

CMD names the default process, stored as metadata.

The final dot is the build context: files Docker may read. COPY takes only what you name.

Stable first, volatile later

Each instruction becomes a cached layer.

Edit app.py, and every layer from the change upward rebuilds.

Copy requirements.txt first, so the heavy pip install stays cached.

For PyTorch-sized images, that’s minutes versus seconds.

Two quiet gotchas

A tag is a sticky note pointing at an image, not the image itself.

Rebuild v5 and the note moves to a new image ID. Release with versions or Git commits.

Empty logs from a running app? Python may be buffering its output.

python -u sends each line straight to docker logs.

The writable layer

Image layers are read-only. Each container gets a thin writable layer on top.

Stop and start the same container: your files are still there.

Remove the container, and its writable layer goes with it.

Data that outlives containers

To keep data, write it somewhere outside the container.

Bind mount: you pick the host folder. Volume: Docker manages the spot.

Remove the container, even with --rm, and the data stays.

Mount big datasets instead of baking them in. Add :ro for read-only.

When memory runs out

--memory=100m sets a ceiling for Pid’s cgroup. It doesn’t reserve a block of RAM.

Pid tries to grab 300 MB…

The kernel steps in and kills it with SIGKILL.

Exit 137 says how it ended. OOMKilled=true says why.

How much time vs. which seats

--cpus=2: about two CPUs’ worth of time, spread across any cores.

--cpuset-cpus="2,3": only CPUs 2 and 3 may run it.

One limits how much, the other limits where. Watch both live with docker stats.

Read the exit code

Killed by a signal? The code is 128 + the signal number.

0 means success. 137 means a forced kill, so check OOMKilled.

A graceful docker stop sends SIGTERM first, so the app can clean up.

How a container reaches the GPU

The container brings your app and the CUDA userspace libraries.

The host brings the NVIDIA kernel driver and the physical GPU.

A CUDA image alone isn’t GPU access. Without --gpus, no device shows up.

--gpus all connects them through the NVIDIA container stack.

Reading nvidia-smi

nvidia-smi is the GPU’s dashboard.

Memory used and compute utilization are two different gauges.

A model can sit in VRAM while the GPU does almost no work.

All together: a mini AI job

One command uses nearly every idea from today:

docker run -d --name day7-ai-job \
  --gpus all --cpus=2 --memory=2g \
  -v ~/ai-infra/day7-gpu-output:/output \
  nvidia/cuda:13.0.0-base-ubuntu24.04 \
  bash -c 'while true; do …; sleep 10; done'

GPU access, a CPU and memory budget, and a mounted output folder.

Every 10 s it checks the GPU and appends a timestamp on the host.

That’s a tiny preview of a Kubernetes Pod.

Debugging, step by step

Start with the main process: is the container running?

Not running? Read the exit code, the logs, and OOMKilled.

Running but unreachable? Check the listen port, -p, and the network.

Reachable but broken? Look at mounts and devices.

The whole picture

A container is a Linux process, started from an image.

Namespaces shape what it sees. cgroups cap what it uses.

Networks reach it, mounts outlive it, and the host lends the kernel and GPU driver.
